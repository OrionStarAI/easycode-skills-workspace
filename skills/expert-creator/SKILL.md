# 创建 Easy Code 专家

把用户描述的职责整理为可复用的个人专家，保存到 Easy Code 的「我的专家」。这是创建专家的技能；专家本身不是技能，也不是专家团。此技能需要 Node.js 18 或更新版本，以及当前会话中可用的文件写入和执行命令能力。

## 理解并设计专家

1. 明确用户希望专家完成的工作、使用场景和期望结果；如果连职责都无法推断，先问一个简短问题。对于可合理推断的细节直接采用合适默认值，用户明确要求创建时无需再次确认。用户明确要求创建时，不要用推荐现有专家代替创建；用户若是要求编辑现有专家，应使用现有编辑入口，不要额外创建同名专家。
2. 写一个清楚的名称和简短描述。编写有实质内容的 `instructions`：说明职责、预期输入、工作步骤、结果格式和必要边界；对于未提供的事实要求先核实或说明不确定性。根据实际任务调整详略，不要只写一句笼统角色提示。涉及发送、发布或更改其他系统时，遵守用户实际授权。
3. 普通办公、写作、研究等任务使用 `promptProfile: "general"`；明显属于软件开发、代码审查等任务时使用 `"coding"`。专家指令会追加到所选基础提示词，不覆盖原有系统规则、用户授权或工具权限。
4. 用 `list_available_skills` 检查已安装并启用的技能，只绑定对职责确有帮助的技能，使用工具返回的准确名称。不要臆造技能；没有合适的技能时可用空数组。若用户指定了必需但缺失的技能，可使用 `search_skill_marketplace` 查找，并通过 `install_skill` 按产品现有的确认流程安装；安装后再次确认已启用。如必需技能无法安装或启用，应说明原因并等待用户决定，而不是声称专家已可用。
5. 默认不填写 `allowedTools`，继承用户当前工具权限。仅在用户要求限制工具时，根据当前会话可用工具的名称填写允许列表；例如只读代码审查可从可用的 `list_directory`、`read_file`、`read_many_files`、`glob`、`search_file_content` 中选择，不包括写入或 shell。不要用其他工具绕过限制；如无法确认工具是否可用，说明该限制需要实际会话验证，不要自行扩大权限。空数组表示不允许任何工具，不表示默认权限。如果绑定的技能需要工具，限制应兼顾技能实际需求；无法满足时明确告诉用户。工具白名单限制专家可调用的工具，并不是工作区硬隔离；搜索工具内部可能启动子进程，不应承诺整个应用绝不启动进程。
6. 仅在用户指定或任务确有必要时设置 `model`、`workspace` 和 `memoryEnabled`。不要把飞书、企微或其他凭据放进专家指令或文件。个人专家保存在本机；不要自动提交到 GitHub 或发布到市场。

## 创建并核实

先把草稿作为 UTF-8 JSON 文件写到临时位置，包含 `name`、`description`、`instructions`、`skills` 和 `promptProfile`；其他字段仅在需要时添加。示例结构如下，内容须依据用户的实际需求编写：

```json
{
  "name": "会议纪要专家",
  "description": "整理会议讨论、决策和待办。",
  "instructions": "根据会议材料梳理主题、关键讨论、决策和待办。对每项待办列出负责人和截止时间；材料没有的信息标为待确认，不要编造。",
  "skills": [],
  "promptProfile": "general"
}
```

`use_skill` 的结果会给出本技能目录和脚本的实际路径。使用那个路径执行以下命令，将占位符替换成实际路径，并按当前 shell 安全引用路径；不要自行编写替代脚本：

```sh
node "<skill-directory>/scripts/create-expert.mjs" --input "<draft-json-path>"
```

脚本会校验草稿，生成新的专家 ID，并写入当前用户的 `~/.easycode-user/experts/`；不会覆盖已有专家。退出成功且输出包含 `id`、`name`、`path` 才表示写入成功。出错时解释原因，不要声称创建成功。完成后删除本次生成的临时草稿；不要删除其他文件。

告诉用户专家名称、工作模式、已绑定技能和明确设置的工具限制。说明可以在「专家 → 我的专家」中查看、编辑、使用及配置飞书或企微；如果页面在创建前已经打开，重新进入「我的专家」以刷新列表。不要把专家写到「我的技能」。
